# Обёртка над Keitaro

Локальное приложение на FastAPI создаёт кампании с двумя потоками через Keitaro Admin API. В браузере можно выбрать страну и оффер для новой кампании, открыть существующую кампанию и опубликовать изменения в отдельном потоке. Сервер проверяет справочники и сохраняет ход операции в SQLite, чтобы её можно было продолжить после сбоя.

## Запуск

Потребуется Python 3.12. Выполните команды из каталога репозитория. Пример для Windows PowerShell.

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
Copy-Item .env.example .env
```

В локальном `.env` укажите значение `KEITARO_API_KEY` из своей учётной записи учебного стенда. Адрес API уже указан в примере. Для SQLite по умолчанию используется файл `keitaro.sqlite3` в текущем каталоге. Примените миграции перед первым запуском и после обновления приложения.

```powershell
.\.venv\Scripts\python.exe -m alembic upgrade head
.\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

В Linux или macOS создайте окружение командой `python3.12 -m venv .venv`, скопируйте настройки через `cp .env.example .env` и в командах установки и запуска используйте `.venv/bin/python`.

## Создание кампании

1. Откройте [создатель кампаний](http://127.0.0.1:8000/). Введите название и двухбуквенный код страны, например AU. Префикс `test_nitsevich_` добавляется к имени автоматически.
2. Найдите оффер по ID или части названия и выберите запись в списке. Форма покажет назначение обоих потоков.
3. Нажмите «Создать кампанию». Первый поток перенаправляет посетителей из выбранной страны на Google, второй отправляет остальной трафик на выбранный оффер с долей 100%. После сверки приложение покажет ID и ссылку на кампанию в админке.

Для учебного стенда используются `KEITARO_DOMAIN_ID=1813`, `KEITARO_GROUP_ID=10332` и `KEITARO_TRAFFIC_SOURCE_ID=836`. Эти значения можно задать в локальном `.env`. Приложение сверяет их с каталогами до создания кампании. Учебный трекер позволяет проверить конфигурацию через API и админку; фактические переходы он не обслуживает.

Если связь оборвалась, используйте «Повторить запрос» в той же вкладке. Параметры и UUID операции сохраняются при перезагрузке страницы. Если соединение не установилось до отправки POST, та же операция продолжится с последнего подтверждённого шага. Если запрос мог дойти до Keitaro, сервер сначала сверит кампанию по ID или стабильному alias и проверит уже созданные потоки. При неоднозначном результате или внешнем изменении форма покажет ошибку для сверки с журналом стенда. «Начать другую кампанию» создаёт новую независимую операцию.

Для прямого вызова используйте `POST /api/campaigns` с типом `application/json` и полями `request_id` (UUID), `name`, `geo_code`, `offer_id`. Сохраняйте тот же UUID и поля для всех попыток одной операции. Маршрут предназначен для доступа через loopback.

## Импорт кампаний и локальный архив

1. Откройте [потоки кампаний](http://127.0.0.1:8000/campaigns) и выберите кампанию. В списке доступны и кампании, созданные напрямую в Keitaro.
2. Нажмите **Fetch streams from KT**. Приложение прочитает кампанию и её потоки, сохранит снимок в SQLite и покажет офферы с долями в порядке стенда. **View in KT** открывает кампанию в админке. При следующем выборе кампании откроется сохранённый снимок. Чтобы получить свежие данные, снова нажмите Fetch.
3. Если в Keitaro удалили привязку, после обновления она появится в локальном архиве этого потока с долей 0%. Если оффер вернут, Fetch восстановит его с опубликованной долей. Офферы со статусом `disabled` сохраняют состояние и вес из Keitaro. Пустой поток тоже виден. Если целиком исчез сам поток, его история сохраняется и снова доступна при возвращении потока с тем же ID.

Fetch делает в Keitaro только запросы чтения. Неудачная загрузка сохраняет предыдущий снимок. При одновременном обновлении кампании устаревший Fetch вернёт HTTP 409. Повторите его для получения нового снимка. Если alias выбранной кампании совпадает с alias операции создания, Fetch возвращает HTTP 409, пока у создателя нет подтверждённого ID кампании в Keitaro. После подтверждения ID можно загрузить уже созданные потоки, даже если создание кампании ещё продолжается. Если создатель обнаружит уже импортированную кампанию с тем же alias, он вернёт HTTP 409 и её ID. Сохранённые потоки можно открыть в списке кампаний.

| Метод и путь | Результат |
|---|---|
| `GET /api/campaigns?offset=0&limit=50` | Страница кампаний из Keitaro |
| `POST /api/campaigns/{id}/fetch` | Обновлённый снимок. Отправьте JSON `{}` с локального адреса приложения |
| `GET /api/campaigns/{id}/streams` | Сохранённые потоки из SQLite с локальными правками, если есть черновик. До первого Fetch возвращается HTTP 404 |

## Черновик потока

На странице кампаний загрузите потоки кнопкой **Fetch streams from KT**. В потоке офферов найдите оффер по названию или ID и нажмите **Add**. **Remove** убирает опубликованную привязку из рабочего состава и показывает для неё 0%. **Bring back** возвращает оффер активным и без закрепления, в конец списка офферов потока. Оставшиеся офферы сохраняют свой порядок. Редактировать можно и пустой поток со схемой `landings`. Для кампании, которую ещё собирает создатель, доступен просмотр. Редактирование откроется после завершения создания.

**Pin** на текущей доле сохраняет веса всех офферов. Закрепление должно допускать распределение 100% между активными офферами. Например, закрепить единственный активный оффер на 60% нельзя, поскольку для оставшихся 40% нет свободного оффера. Если черновика нет, приложение сразу сохраняет закрепление в SQLite. Оно переживает перезагрузку, а кнопки **Push to KT** и **Cancel** остаются скрытыми. Если черновик уже открыт, закрепление входит в него и отменяется вместе с другими правками.

Если ввести **другую долю** от 1 до 100% и нажать **Pin**, приложение закрепит её и поровну распределит остаток между свободными активными офферами. Такой же пересчёт выполняется при добавлении, удалении или возврате активного оффера. Остаток от целочисленного деления получают последние свободные офферы по порядку. **Unpin** снимает закрепление в черновике и сохраняет текущие веса до следующего пересчёта. Попытка снять отсутствующее закрепление через API возвращает HTTP 409.

Удаление оффера в состоянии `disabled` переносит его в архив с долей 0% и сохраняет доли активных офферов. Так можно удалить и последний отключённый оффер в полностью отключённом потоке. **Bring back** возвращает его активным и запускает пересчёт. Если удаление уберёт последний активный оффер или закрепления оставят недостаточно процентов для остальных, форма объяснит причину и сохранит правки. При отмене добавления единственного нового оффера в ранее пустой поток восстановится пустой состав.

Черновик хранится в SQLite отдельно для каждого потока. Индикатор показывает неопубликованные изменения, в том числе после перезагрузки страницы. **Cancel** отменяет все изменения выбранного потока и возвращает последний подтверждённый состав, доли и закрепления. Добавление нового оффера и его удаление взаимно отменяются. Если других изменений не было, индикатор исчезнет.

Если у кампании есть черновики, **Fetch** предлагает оставить их либо отбросить и загрузить потоки заново. Черновики сбрасываются только после успешного обновления. Если в другой вкладке состав или черновик успели измениться, приложение вернёт HTTP 409 и предложит сверить сохранённые потоки. Все действия с черновиком сохраняют изменения локально. Для поиска и добавления оффера приложение читает каталог Keitaro.

## Публикация потока

1. Откройте кампанию и нажмите **Fetch streams from KT**. В нужном потоке добавьте или удалите оффер либо введите и закрепите новую долю. Проверьте порядок и цифры в таблице.
2. Нажмите **Push to KT** у выбранного потока. Сервер перечитает этот поток и сравнит ID офферов, их порядок, доли и состояния с исходным снимком черновика. При внешнем изменении вернётся HTTP 409, черновик сохранится. Для сверки откройте **View in KT**. Чтобы принять состав стенда, используйте Fetch с явным подтверждением сброса черновиков кампании.
3. При совпадении исходного состава сервер отправит `PUT /streams/{id}` с полным массивом `offers`. В него входят `offer_id`, `share` и `state` для каждой оставшейся привязки, включая отключённые. Архивные привязки остаются в локальной базе. Публикуются доли из таблицы, в том числе неполная сумма активных долей или пустой список. Закрепления хранятся в SQLite. Если в Keitaro изменили долю или состояние оффера, Fetch снимет закрепление у этой привязки. Перестановка офферов сохраняет закрепления. Если в черновике изменились только закрепления, для его подтверждения достаточно исходной сверки через GET.
4. После PUT сервер ещё раз прочитает поток. При точном совпадении с целью исчезнет индикатор черновика, а подтверждённые доли и закрепления сохранятся после перезагрузки страницы. У соседних потоков останутся свои составы и черновики.

Предварительный GET обнаруживает изменения, сделанные к моменту сверки. Стенд не поддерживает условный PUT. Внешнее изменение между GET и PUT всё ещё возможно.

Если результат записи неизвестен, нажмите **Сверить с Keitaro**. Сервер выполняет GET и сравнивает опубликованный состав с целью и исходным снимком. Если цель уже на стенде, публикация завершается. Если стенд сохранил исходный состав, черновик остаётся доступен для отдельного ручного Push. При третьем составе приложение показывает конфликт. Пока сверка невозможна, черновик этого потока защищён от изменения и сброса, в том числе после перезапуска приложения.

Для прямого вызова используйте `POST /api/campaigns/{campaign_id}/streams/{stream_id}/push`. Передайте JSON `{"expected_revision": 7}`, подставив текущую `revision` выбранного потока из сохранённого снимка. То же действие для потока с `push_pending=true` запускает сверку.

### Сквозная проверка после установки

Создайте собственную кампанию с тестовым префиксом и двумя потоками. Откройте её в редакторе, нажмите Fetch, добавьте второй оффер в поток с офферами и нажмите Push у этого потока. В админке проверьте доли 50/50, геофильтр и адрес редиректа соседнего потока. В журнале стенда найдите GET, PUT и контрольный GET по ID изменённого потока. В теле PUT должно быть только поле `offers`.

Удалите один из двух офферов и опубликуйте изменение. В редакторе он появится в архиве с долей 0%. Нажмите **Bring back** и снова опубликуйте поток. Для проверки конфликта откройте следующий черновик и измените долю в админке до Push: редактор должен сохранить черновик и показать конфликт. Учебный стенд позволяет проверить эти данные и журнал запросов через админку без реального рекламного трафика.

**Пример из видео.** Исходный порядок офферов — `3749`, `11111`, `11112`, `3717`, по 25% каждому. Оператор удаляет первые два в Keitaro и нажимает **Fetch**. У `11112` и `3717` остаётся по 25%, а удалённые офферы попадают в архив с 0%. **Pin** на текущих 25% у `3717` сохраняет долю `11112` равной 25%. После **Bring back** для `3749` в **Push** уходит список `11112` (37%), `3717` (25%), `3749` (38%). Оффер `11111` остаётся в архиве с 0%. Этот пример можно воспроизвести локальным тестом `tests.test_publishing.PublishingTests.test_video_fetch_pin_current_share_restore_and_push`.

## Проверка справочников

Откройте [интерактивную документацию приложения](http://127.0.0.1:8000/docs). Методы возвращают массив записей с полями `id` и `name`.

| Адрес | Результат |
|---|---|
| `GET /api/domains` | Домены |
| `GET /api/groups` | Группы кампаний |
| `GET /api/traffic-sources` | Источники трафика |
| `GET /api/offers` | Офферы |
| `GET /api/offers?q=18001` | Поиск по ID или вхождению строки в название |

Для проверки поиска на своём стенде откройте список офферов, скопируйте ID одной записи, затем попробуйте фрагмент её названия. Пустой результат поиска возвращается как `[]`. Если стенд отклонил ключ, обёртка вернёт HTTP 502 с кодом ответа Keitaro. При тайм-ауте она вернёт HTTP 504.

## Локальные тесты

```powershell
.\.venv\Scripts\python.exe -m unittest discover -v
```

На Linux и macOS используйте `.venv/bin/python -m unittest discover -v`. Тесты поднимают приложение с временной SQLite-базой, применяют миграции и подменяют HTTP-транспорт Keitaro. Они проверяют справочники, создание и порядок потоков, повторные запросы, восстановление создателя после сетевых сбоев, импорт, архив, восстановление черновиков, пересчёт весов, сверку до и после Push, конфликты и восстановление после потери ответа. Ключ для локальных тестов задан в фикстуре.
